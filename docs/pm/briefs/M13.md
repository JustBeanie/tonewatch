## Integration facts (verified by PM)
- **Channel loop:** `Channel.run` calls `engine.feed(frame.samples)` per frame and uses `output.frames` (spectrum) and `output.detections` (the matcher's `Detection`: `toneset_id`, `detected_at_s`, `segments`, `early`).
- **Segmenter output:** `Segmenter.feed` returns `SegmenterUpdate(opened, extended, closed)` of `ToneSegment(freq_hz, start_s, end_s, mean_purity, closed, excess_s)`.
- **Engine output:** if the engine output doesn't already expose the segmenter update, add it as a new field. This is additive: existing consumers and golden tests must not change.
- **Migrations:** the latest is `0003_audit_events.py`, so yours is `0004_discovered_tones.py`. The migration no-drift regression test must keep passing.
- **Dual-tone hardware:** the segmenter sees one dominant peak per frame, so simultaneous dual-tone (DTMF-like) signals appear as rapid alternation or low purity. Reject them via the purity gate and a minimum segment length, not new DSP.

## Required
1. **M13.1 `backend/src/tonewatch/dsp/discovery.py`**, pure and synchronous, fed per channel:
   - `DiscoveryTracker.feed(update: SegmenterUpdate, detections: Sequence[Detection], now_s: float) -> list[ToneCandidate]`.
   - **Grouping:** buffer **closed** segments that pass the purity and level gates (reuse the detector's defaults). Group segments separated by ≤ `max_gap_s` (default 0.5 s) into candidate sequences of 1–5 tones.
   - **Candidate shapes:**
     - two-tone: every segment 0.3–3.0 s
     - long tone: one segment ≥ 2.0 s
     - other N-tone: each segment 0.3–3.0 s
   - **Finalize:** a candidate is final once `now_s` exceeds its last segment end + `max_gap_s`.
   - **Suppress matched pages:** if any `Detection` covers a candidate segment's time span (overlap with its `segments`), drop that candidate. Stacked pages (a known set plus an unknown set in the same call) must still yield the unknown part.
   - **Bounds:** 250–3000 Hz. Bounded memory: a cap on buffered segments, with the oldest dropped.
2. **M13.2 Clustering + storage.**
   - **Cluster rule:** a candidate joins a cluster when tone count matches and every tone agrees within `tol_pct` (default 1.5 %) of the cluster's running mean. Otherwise it creates a new cluster.
   - **Stored per cluster:** mean frequencies, median durations, count, first/last seen (UTC), source ids, observed frequency spread, status (`new|dismissed|promoted`), and `best_clip_recording_path`.
   - **Order independence:** the same observations in any order must produce the same clusters within tolerance. Use a deterministic assignment, e.g. nearest cluster with tie-breaks.
   - **Persistence:** SQLAlchemy model `DiscoveredTone` + migration `0004`, and repository functions. Persist from the pipeline side via the persistence layer with shielded commits (follow `persistence.py` patterns), never from the DSP.
   - **Caps:** at most 1,000 clusters. The retention job prunes the oldest-unseen `new`/`dismissed` clusters beyond the cap and deletes their clips. `promoted` clusters are kept.
   - **Dismissed:** a cluster never re-surfaces as `new`, but its count still increments.
3. **M13.3 Evidence clip (setting `discovery.clip`, default on).**
   - **Clip:** for each **new** cluster, and when a later observation has higher mean purity, keep one clip. It covers the tones plus up to 15 s after, captured through the existing ring buffer and encoder under `recordings/discovered/<cluster_id>.mp3`.
   - **Replacement:** replace the clip atomically; the old one is deleted only after the new one is written.
   - **Retention:** clips count toward recording retention.
   - **Safety:** never delete any file except that cluster's own clip, and path-check against the recordings root, as retention already does.
4. **M13.4 API + WS.** Everything requires auth, and CSRF for cookie sessions on state changes.
   - `GET /api/discovered-tones?source=&since=&status=` returns the paged list.
   - `GET /api/discovered-tones/{id}` returns one cluster.
   - `POST /api/discovered-tones/{id}/promote` returns a **draft** `ToneSet` and does **not** persist it:
     - frequencies = cluster means
     - `tol_pct` = clamp(max(1.5, observed spread % × 1.5), 0.5, 5)
     - `min_s` = 0.8 × median duration, `max_s` = unset
     - name `Discovered <f1>/<f2> Hz`, and a slug id that's unique against existing tone sets

     It marks the cluster `promoted` only when the tone set is actually saved. Record the cluster id on the save path (an optional `discovered_tone_id` in the create request).
   - `POST /api/discovered-tones/{id}/dismiss`.
   - `DELETE /api/discovered-tones/{id}` also deletes its clip.
   - `GET /api/discovered-tones/{id}/clip` supports Range, like recordings.
   - **WS:** a `tone_discovered` event on new clusters only, never per observation.
   - **Audit:** audit entries for promote, dismiss and delete.
   - Regenerate the OpenAPI client and WS message types (`just gen-api`).
5. **M13.5 Web "Discovered tones" page.**
   - **Table:** tones (Hz), durations, times heard, last heard (relative + absolute), source, clip player, and actions **Create tone set** (opens the existing tone-set form pre-filled with the draft) and **Dismiss** (with confirm).
   - **Filters:** status and source.
   - **Dashboard:** a badge counts `new` clusters, live via WS.
   - **Tests:** jsx-a11y clean; Vitest covers rendering, filters, the promote → form pre-fill flow, and the dismiss confirm.
6. **M13.6 Notifications (all default OFF).**
   - A `tone_discovered` webhook event type and an MQTT topic `.../discovered`, both opt-in per alert target via a new `events` list that defaults to the current behaviour.
   - An HA discovery `event` entity `tone_discovered`, only when enabled.
   - Payloads carry frequencies, durations, count, source and the clip URL (absolute when `public_base_url` is set; M10a adds that setting, so if it hasn't landed yet use the relative path plus `recording_path_relative: true`, same as recordings).
7. **M13.7 Settings + CLI.**
   - **Settings:** `discovery.enabled` (default true), `discovery.clip` (default true), minimum durations, `max_gap_s`, `tol_pct`, and per-source `discovery_enabled` (default true). They're validated in config models and hot-applied like tone sets.
   - **CLI:** `tonewatch analyze file.wav --config config.yaml --discover` prints unmatched candidates (table and `--json`).

## Tests (definition of done for DSP correctness)
- **Golden scenarios** (data-driven, like the existing suite) using `dsp/generator.py`:
  - an unknown two-tone → exactly 1 cluster, count 1
  - a known tone set → 0 candidates
  - an unknown two-tone repeated 3× with ±0.5 % jitter → 1 cluster, count 3
  - two unknown pages whose tones differ by more than 2× `tol_pct` → 2 clusters
  - a stacked known + unknown in one call → 1 `ToneDetected` + 1 cluster
  - an unknown long tone of 4 s → 1 cluster
  - a too-short 0.15 s blip → 0
  - a noisy unknown two-tone at SNR 10 dB → 1 cluster
- **Zero candidates** on the existing 1-hour synthetic voice/noise corpus (in `just test-slow`, like the M2 false-positive run) **and** on a 10-minute voice sample in the fast suite.
- **Hypothesis:**
  - clustering is order-independent
  - the tracker never exceeds its memory caps
  - no candidate ever overlaps a matched detection span
- **End to end, integration through the real `create_app` lifespan** (not an injected channel factory):
  1. a file source plays an unknown two-tone
  2. the cluster is persisted (wait for **persisted** state with a bounded timeout)
  3. the clip exists
  4. `POST promote` → create the tone set via the API with `discovered_tone_id` → the cluster is `promoted`
  5. replay the same file → a `ToneDetected` for the new set **and** no new discovery
- **API:** auth/CSRF rejection paths, Range on clips, and delete removing only that clip. A path-traversal attempt on the clip id must be rejected.
- **Performance:** extend `just bench` with discovery enabled. The 200-set/10-minute benchmark must stay ≥ 20× realtime, and the numbers are recorded in `docs/benchmarks.md`.
- **Security docs:** add discovery clips (radio audio at rest) and the new endpoints to the threat model. Update ASVS rows only with real snippet + test evidence, and keep `security_scorecard.py --check` green.
