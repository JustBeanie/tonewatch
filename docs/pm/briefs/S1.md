# Brief: S1 Baseline OWASP SAMM + DSOMM assessment

**From:** PM (Claude) · **To:** Codex engineer · **Model:** gpt-5.6-luna, medium

## Goal
Produce an **honest baseline** security maturity assessment of the repo as it stands today (M0 + M1 done), plus tooling that keeps the scores tied to evidence. Low scores are expected and correct. **Inflated scores fail review.**

Before starting, read `AGENTS.md` (Local mode, Tooling), `PLAN.md` → "Security assurance: OWASP SAMM + DSOMM" and "S track", and `docs/PROGRESS.md`.

## In scope
S1 only. **Do not add scanners or CI jobs**; that is S2. Do not change app code.

## Sources (you have network; use the official material, don't write from memory)
- **SAMM v2:**
  - The model on https://owaspsamm.org/model/ gives the 5 business functions, 15 practices, streams A/B and maturity levels 1–3.
  - For question wording, use the official assessment questions from the SAMM toolbox, or the SAMM core data on GitHub under `owaspsamm`.
  - Record the exact source URL and version in `docs/security/samm/README.md`.
- **DSOMM:**
  - Activity data comes from the official data repo `devsecopsmaturitymodel/DevSecOps-MaturityModel-data`. Pin a commit SHA.
  - Assess **only levels 1 and 2**, across all dimensions. Record the pinned SHA.
- If a source is unreachable, write `BLOCKED:` with the URL tried, rather than inventing structure.

## Deliverables
1. **`docs/security/samm/assessment.yaml`**
   - One entry per practice × stream (30 entries). Each holds:
     - `function`, `practice`, `stream`
     - `current_level` (0–3, where 0.5 steps are allowed as SAMM does)
     - `target_level` (from the PLAN target table)
     - `answers` (the question and the chosen answer text)
     - `evidence` (a list of repo-relative paths or URLs)
     - `na_justification` (null unless N/A)
     - `assessed_on: 2026-09-10`
   - Ground rules for scores:
     - A level can only be claimed when concrete evidence exists in the repo **today**, such as `.github/workflows/codeql.yml`, `SECURITY.md`, `renovate.json`, pre-commit hooks or the ruff `S` rules.
     - Planned work counts as 0 and is named in `gaps.md`.
     - Items that don't fit a solo open-source project (formal training programmes, dedicated incident teams, etc.) get `na_justification`.
2. **`docs/security/dsomm/activities.yaml`**
   - Each activity id and name records `dimension`, `subdimension`, `level`, `status: implemented|partial|planned|na`, `evidence`, `planned_in` (the S# or M# task that will implement it) and `notes`.
3. **`scripts/security_scorecard.py`**
   - Validates both YAML files against a schema, using pydantic models inside the script.
   - **Fails** (non-zero exit) when a claimed level above 0 or an `implemented` status has no evidence, or when an evidence path doesn't exist on disk. URLs are allowed without fetching.
   - Also fails when an N/A entry lacks justification, or when a target is below the PLAN table.
   - Regenerates `docs/security/samm/scorecard.md` (a table per business function with current, target and gap, plus an overall average) and `docs/security/dsomm/scorecard.md` (implemented/partial/planned counts per dimension and level).
   - Regenerates `docs/security/gaps.md`: every practice below target and every planned or partial DSOMM activity, with owner task, sorted by owner task order in the PLAN dependency chain.
   - `--check` mode compares generated files against the committed ones and fails on drift, like the API client drift check.
4. **Tests** in `backend/tests/unit/test_security_scorecard.py` (import the script via importlib). They cover: a valid fixture passes; missing evidence fails; a nonexistent evidence path fails; N/A without justification fails; and generated markdown is deterministic.
5. **`justfile`:** add a `security-scorecard` recipe (`--check`) and include it in `check`. Make sure ruff, ruff-format and mypy cover `scripts/`. Extend the pre-commit and just lint paths if they only cover `backend/`.
6. **`docs/security/README.md`** explains the three models and how ASVS relates, how to re-assess, and the rule that evidence must exist.
7. **`docs/PROGRESS.md`:** tick S1 only after the Definition of done passes.

## Definition of done
- `just check` exits 0 (including the new scorecard `--check`).
- pre-commit over all files exits 0 with no unexpected skips. `git add` is denied in the sandbox, so use `pre-commit run --files` over `git ls-files -co --exclude-standard`.
- The final message includes:
  - A table: SAMM current average vs target average per business function.
  - DSOMM implemented / partial / planned counts per dimension.
  - The 5 biggest gaps.
  - Any `BLOCKED:` items.
  - Unfiltered tails of the verification commands.
