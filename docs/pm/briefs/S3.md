# Brief: S3 STRIDE threat model (SAMM Threat Assessment L2)

**From:** PM (Claude) · **To:** Codex engineer · **Model:** gpt-5.6-luna, medium

## Goal
Produce a **code-grounded** STRIDE threat model of ToneWatch as it exists now (M0–M5), in OWASP Threat Dragon format. Map every threat to either an existing mitigation **with a proving test**, a new tracked task, or an accepted risk. It will be the input for the S4 ASVS audit, so accuracy matters more than volume.

Before starting, read `AGENTS.md`, `PLAN.md` (Security assurance section, the S track, M7–M11 for planned surfaces), `docs/security/README.md`, `docs/security/gaps.md`, `docs/security/accepted-risks.md`, `docs/pm/carryover.md` (the S4 notes), and **the actual code**:
- `backend/src/tonewatch/api/` (all of it)
- `integrations/`
- `sources/`
- `pipeline/`
- `recording/`
- `config/store.py`
- `settings.py`
- `logging.py`

Also read the API security tests in `backend/tests/integration/test_api_*.py`.

## Hard rule on evidence
Every "mitigated" status must cite the code location (`path:line`) **and** the test function that proves it. If no test exists, the status is `partial`, and a gap is recorded. A mitigation you can't point to doesn't exist.

## Deliverables
1. **`docs/security/threat-model/tonewatch.json`:** a valid OWASP Threat Dragon v2 model. It holds one data-flow diagram with these elements.
   - **Actors:** LAN user or browser, the HA frontend via ingress, the HA Supervisor, the HA integration (future, M11), an attacker on the LAN, and a malicious audio or stream source.
   - **Processes:** FastAPI app (REST + WS), auth middleware, supervisor/channels, recorder/encoder, retention job, zeroconf responder, Supervisor discovery client, and the alert dispatcher (planned M7, marked out of scope for status but threat-listed).
   - **Stores:** `config.yaml`, `api_token` file, password hash and sessions, SQLite DB, recordings directory, and logs.
   - **Flows:** each with protocol, authentication and whether it crosses a trust boundary.
   - **Trust boundaries:** LAN ↔ host, HA ingress ↔ add-on, add-on ↔ Supervisor, container ↔ host devices (`/dev/snd`, USB), app ↔ network stream origin, and app ↔ `rtl_fm` subprocess.

   Validate the JSON by loading it with a small schema check in the test below.
2. **`docs/security/threat-model/README.md`:**
   - how to open the model in Threat Dragon
   - scope and assumptions: self-hosted, a single household or department, HA as the primary deployment
   - a table of **every threat**: id `TM-###`, STRIDE category, element, description, likelihood and impact (low/med/high), status (`mitigated` / `partial` / `open` / `accepted` / `planned`), evidence (code path:line + test name), and the owning task (S4/S5/M7/M8/M10/M11 or an existing M#)
   - **You must cover at least:**
     - **Spoofing:** ingress header spoofing; token theft from the data dir; WS handshake without auth; zeroconf impersonation (a rogue `_tonewatch._tcp` luring the future HA integration into sending credentials, owned by M11).
     - **Tampering:** config write races; path traversal in recording download; malicious WAV or stream causing parser exploits in PyAV/FFmpeg; `rtl_fm` argv injection via config.
     - **Repudiation:** no audit log of config changes, or who triggered test pages.
     - **Information disclosure:** secrets in logs; recordings of radio traffic exposed on the LAN; OpenAPI and docs exposure; error leakage; zeroconf TXT contents.
     - **Denial of service:** upload size; WS connection and queue exhaustion; slow-loris on uvicorn; decompression or long-audio bombs via stream; disk fill via recordings (retention); CPU via many tone sets or channels; login throttle memory growth keyed by IP.
     - **Elevation of privilege:** script alert targets (M7) as remote code execution; the container running as root (M8); add-on permissions (`hassio_api`, `map: media:rw`) (M10); SSRF via webhook targets (M7) and via stream URLs (**today**: can a user point a stream source at `http://169.254.169.254/` or internal services?).
3. **`docs/security/gaps.md`:** add every `open` or `partial` threat, with its owner task. Record accepted risks in `docs/security/accepted-risks.md` using the existing format (id, rationale, expiry ≤ 90 days).
4. **SAMM re-score:** update `docs/security/samm/assessment.yaml` for **Threat Assessment** (streams A: Application Risk Profile and B: Threat Modeling) and **Architecture Assessment** with the new evidence, following the pinned official answer options. Regenerate the scorecards (`scripts/security_scorecard.py`).
5. **`backend/tests/unit/test_threat_model.py`:**
   - the JSON parses and has the required top-level Threat Dragon keys
   - every threat id in the README table appears in the JSON and vice versa
   - every `mitigated` row names a test function that **exists** in `backend/tests` (grep via `ast`)
   - every `path:line` evidence reference points to an existing file with at least that many lines
   - every `open` or `partial` row appears in `gaps.md`

   This keeps the model honest as the code changes.

## Explicitly look for real vulnerabilities
While modelling, if you find a concrete exploitable issue in current code (the stream-URL SSRF question above is a likely candidate), **don't fix it in this task**. Record it as `open`, severity-rated, with a minimal reproduction in the README. The PM will schedule the fix. List all such findings at the top of your final message.

## Constraints
- No application code changes. Only `docs/security/**`, the new test, and the scorecard regeneration.
- Don't modify PM-owned files: `docs/pm/*`, `.github/workflows/*`, `scripts/license_check.py`.

## Definition of done
- `just check` exits 0 (including the new test and the scorecard `--check`); run it last and paste the tail.
- pre-commit over all files exits 0.
- The final message covers: the count of threats per STRIDE category and per status; the concrete vulnerabilities found (if any) with severity; the SAMM Threat Assessment before/after.
